# Workflow

How the owner and Claude work together. The owner spends a few hours a week deciding; Claude writes all the code; CI judges every result.

## Where things happen

- **Conversation:** the owner and Claude work in a claude.ai conversation, the hub, until Claude Code Projects is available on the owner's account, then in a project named "CodinGame Bot Lab" ([ADR 0008](adr/0008-claude-hub.md)). The owner asks for work, reads results and decides there.
- **Repository:** the durable record. Decisions go into ADRs, plans into `docs/`, experiment results into the journal, reports of training runs into `games/<game>/training/`. Nothing important lives only in a conversation.
- **GitHub:** Claude opens a pull request from a `claude/` branch for every change. CI and the SPRT workflow judge it; the owner approves the merge in the conversation and Claude carries it out ([ADR 0023](adr/0023-chat-approved-merges.md)). The owner rarely needs to open GitHub for anything else; notifications for this repository are set to "Participating" to avoid duplicates.
- **CodinGame:** Claude submits a release through CodinGame's API only on the owner's approval of that release in the conversation, and records its rank in the release's journal entry when the ranking games end ([ADR 0047](adr/0047-codingame-api.md)). The owner may still paste a release himself; a rank he reports is recorded the same way, and Claude never asks him for one ([ADR 0036](adr/0036-ranks-optional.md)).

## A round of work

The owner starts each round in the conversation; no scheduled session runs ([ADR 0033](adr/0033-no-daily-scheduled-session.md)). For bot strength, a round looks like this (about one to two hours of the owner's time):

1. Claude reports the results since the last round and proposes two or three experiments, or the owner describes an idea.
2. Claude implements each experiment in its own pull request; CI runs the tests and the SPRT workflow runs the smoke test and the SPRT.
3. The owner approves merging accepted candidates. A rejected one comes back reduced to its journal entry, which is merged too, so the failure stays on record.
4. When a release is published, Claude submits it to CodinGame through the API once the owner approves that release in the conversation, then reads and records its rank when the ranking games end ([ADR 0047](adr/0047-codingame-api.md)). The owner may still paste the file (attached to its GitHub release) himself.

Other work, such as tooling, documentation or training runs, takes the same path: a pull request from a `claude/` branch, CI as judge, the owner approving the merge. Bot strength work is paused from 2026-10-09 while phase 5 is built.

## A new game

The owner names each new game; it then goes through eleven stages, from intake to retrospective, and the owner decides at the end of every stage ([ADR 0035](adr/0035-new-game-lifecycle.md)). The [new game playbook](NEW_GAME.md) gives each stage's outputs, checklist and gate; the game's state is in `games/<game>/ROADMAP.md`, and skill `new-game` names the next stage. Claude does not open codingame.com: the owner pastes the statement and the other pages each stage needs.

## An experiment, step by step

The rules are in [ADR 0012](adr/0012-evaluation.md).

1. On a branch `claude/<game>-eNNN-<short-name>`, change the bot and screen it locally against the current release with the game's arena (at CodinGame's exact time limits, like every evaluation, [ADR 0042](adr/0042-official-time-limits-and-800-pairs.md); for A Code of Ice and Fire, at CodinGame's speed and real limit, with the scale and tolerance that `scripts/calibrate.sh ice-and-fire` prints for this machine, [ADR 0048](adr/0048-ice-and-fire-codingame-speed.md)). Then freeze it as the candidate: `scripts/new-release.sh <game> <bot>` writes two files ([ADR 0045](adr/0045-minified-releases.md)): `games/<game>/releases/<game>-vNNN.rs`, the minified bundle that is pasted into CodinGame (unused items removed and names shortened with rustc 1.90.0, which must be installed: `rustup toolchain install 1.90.0`), and `games/<game>/readable/<game>-vNNN.rs`, the same bundle with its comments (it may be over the size limit), and plays them against each other with a fixed seed and iterations (`scripts/check-minified.sh`: the same answers every turn); point the game README's `**Current release:**` line and the root README's games table to it (`scripts/check-docs.sh` checks them).
2. Start the journal entry `games/<game>/journal/ENNN-<short-name>.md` from the template: hypothesis, change, and the line `release: <game>-vNNN`. Open the pull request.
3. CI checks the release and its readable copy (both frozen once merged, true to the sources, playing the same games), and the SPRT workflow runs the smoke test and the SPRT against the previous release, then posts the result on the pull request. Both play at CodinGame's exact time limits ([ADR 0042](adr/0042-official-time-limits-and-800-pairs.md)), or, for A Code of Ice and Fire, at its speed and real limit, calibrated on the runner at the start of the job ([ADR 0048](adr/0048-ice-and-fire-codingame-speed.md)), so an accepted candidate needs no confirmation at full time. Locally, `scripts/sprt.sh <game> <candidate.rs>` runs the same test. With `RECORDS_DIR` set to a new or empty folder (relative to the repository root), the script keeps a sample of each step's games as game records. `RECORDS_SAMPLE` games are kept per step, 10 by default, plus every game that ended in a fault; `scripts/league.sh` does the same per pair of bots. The workflows set it and upload the folder as the artifacts `game-records-<game>` (`league-game-records-<game>` for the league), kept 30 days, for the studio's history ([ADR 0027](adr/0027-game-records.md)). When a push to `main` adds a release, the `archive.yml` workflow adds the league sample and the SPRT sample of the release's pull request (the latest of each still kept from its branch) to the game's archive, the one artifact `arena-games-<game>` kept 90 days and uploaded again weekly before it expires; the older copies are deleted ([ADR 0031](adr/0031-arena-games-archive.md), [ADR 0038](adr/0038-incremental-league.md)). For a game with a nightly league, the push adds the SPRT sample only; the night that first plays the release adds its league sample ([ADR 0049](adr/0049-parallel-evaluations-and-nightly-league.md), decision 7).
4. **The league, once the SPRT accepts** (a game with a nightly league, `LEAGUE_NIGHTLY=true` in its `evaluation.env`, skips steps 4 and 5: see "The nightly league" below) ([ADR 0038](adr/0038-incremental-league.md)): a second job of the SPRT workflow, `<game>: league`, plays the new release against its previous release, the game's fixed opponents (`LEAGUE_FIXED`) and the `LEAGUE_NEAREST` bots nearest to it in rating, `LEAGUE_PAIRS` pairs each (800, [ADR 0042](adr/0042-official-time-limits-and-800-pairs.md)), at the SPRT's time limits (about 3 to 3.5 hours for Ultimate Tic-Tac-Toe, A Code of Ice and Fire's depends on its bot's game length and fits the job's limit of 300 minutes only if a game averages 5.6 s or less, to be measured with the first search bot), then replays the canary pairing, if the game has chosen one (`LEAGUE_CANARY`). It posts a comment with the report and the new result lines. The release's faults fail the check `SPRT passed`, with the SPRT's rule; a canary result outside its stored interval is a warning annotation and a line of the comment, never a failure. Locally, `scripts/league.sh <game> vNNN` plays the same league.
5. Claude copies the results into the pull request: the comment's lines, verbatim and in order, at the end of `games/<game>/league.jsonl` (never through `jq` or anything that rewrites JSON: the seeds are 64-bit numbers), the leaderboard regenerated with the command in the comment (`games/<game>/LEADERBOARD.md`), and the SPRT result into the journal entry. Only Markdown and the results file change, so the SPRT workflow reuses its results instead of running again; re-running a job on GitHub does test again, for a failure caused by the machine, and every run posts its result on the pull request. `LEADERBOARD.md` is generated on Linux: the gate runs on `ubuntu-latest`, and the last digit of a rating could differ with another platform's math library. The check `League results` (`scripts/league-check.sh`, part of `SPRT passed`) fails until the results file holds a pairing of the new release and `LEADERBOARD.md` is the one generated from the file. It also runs when a pull request changes the results, the leaderboard, the journal index, the settings or the arena; a game without `league.jsonl` passes with a notice. For a game with a nightly league the check no longer asks for the release's pairings, only for a leaderboard that matches the results file.
6. Accepted: merged on the owner's approval; the release workflow publishes the version. Rejected or inconclusive: Claude removes the release file, its readable copy and the bot change, sets `release: none` and `decision: dropped`, and the entry is merged on the owner's approval.

### The league's bootstrap and replays

The league of a game starts from a replay of its history ([ADR 0038](adr/0038-incremental-league.md), decision 8): the baseline bots and then the releases join one at a time, in order, each playing as a new release would, at the league's time limits. The League workflow (`league.yml`), started by hand, plays a list of bots in one job: inputs `game`, `bots` (space-separated names in order, for example `greedy v001 v002`) and `stop_after_minutes` (default 140; no bot starts after it, since a job lasts 6 hours at most: set it to 360 minus the build minus the longest bot's time, about 140 for Ultimate Tic-Tac-Toe at 800 pairs, and for A Code of Ice and Fire after measuring its first search bot's league, [ADR 0042](adr/0042-official-time-limits-and-800-pairs.md)). Each bot sees the lines of the bots before it, and never a release after it. The job writes nothing to the repository: it prints each bot's new lines between `---- new results of <bot> ----` and `---- end ----` in its log and in the job summary, and says which bots remain (`Stopped before <bot>: ... Next: ...`). Claude reads the lines from the log (skill `github-api`), copies them into `games/<game>/league.jsonl`, regenerates `LEADERBOARD.md` and opens a pull request, then starts the next run with the bots that remain; the next run sees the committed lines only once that pull request is merged. The same workflow replays a release after a change of the league's settings. The canary is chosen when the bootstrap is done.

A replay of the whole history at new settings may instead keep the stored pairings ([ADR 0048](adr/0048-ice-and-fire-codingame-speed.md), decision 5, for A Code of Ice and Fire), so that it runs in parallel. The League replay workflow (`league-replay.yml`), started by hand with inputs `game` and `shards` (15 by default, at most 20), splits the pairings of `games/<game>/league.jsonl` over that many jobs (`scripts/league-replay.sh GAME SHARD SHARDS`). Each job calibrates its runner when the game's settings say so and plays its pairings again: the same two bots, the stored seed, `LEAGUE_PAIRS` pairs. A last job merges the shards in the stored order (`scripts/league-replay.sh --merge`) and prints the new file between `---- replayed league.jsonl ----` and `---- end ----` in its log, with the leaderboard in the job summary. A shard that failed leaves the merge failing: re-run the failed jobs. Claude replaces `games/<game>/league.jsonl` with the merged lines, regenerates `LEADERBOARD.md` and opens a pull request.

### The nightly league and the weekly branch

A game with `LEAGUE_NIGHTLY=true` (A Code of Ice and Fire; Ultimate Tic-Tac-Toe keeps the release-pull-request league above until its calibration is merged, [ADR 0049](adr/0049-parallel-evaluations-and-nightly-league.md), decision 8) plays no league on a release's pull request. Its release merges on the SPRT, the required checks and the owner's approval. Its rating arrives overnight, on the branch `league-results`, and reaches `main` in the weekly pull request.

**The night.** The workflow `league-nightly.yml` starts at 02:00 UTC and calls `league-night.yml` for each such game, so that each game has its own runners and budget: `LEAGUE_NIGHTLY_RUNNERS` (6) runners for `LEAGUE_NIGHTLY_MINUTES` (180) minutes ([ADR 0050](adr/0050-league-anchor-target-and-budget.md)). The steps are in `scripts/league-night.sh`:

1. The plan: from the current results (`games/<game>/league.jsonl` on `league-results`, else on `main`), the arena's `plan` chooses the pairings. Bots without games first play the opponents of [ADR 0038](adr/0038-incremental-league.md) (`LEAGUE_PAIRS` pairs each); the budget that remains (`LEAGUE_NIGHTLY_PAIRS` is its upper bound) goes 80% to pairs near the top whose order is least certain and 20% to the other bots (`LEAGUE_LOW_SHARE`). The precision share stops once the top `LEAGUE_TOP` bots' 95% intervals are within `LEAGUE_TARGET_MARGIN` Elo, measured from `LEAGUE_ANCHOR` (`v001`). The lines are shared between the runners.
2. Wave 1: one job per runner plays its lines, calibrated on its own runner ([ADR 0048](adr/0048-ice-and-fire-codingame-speed.md)). The night has one budget of time (`LEAGUE_NIGHTLY_MINUTES`, 180 minutes) from the start of the plan. A runner starts no line once 50 minutes less a line's 20 would be left (that is, after about minute 110 of the night, and after about 90 minutes of its own job), so that the merge, wave 2 and the publication fit; each finished line is written at once, and the play step has a limit 5 minutes below its job's, so a job stopped at its limit keeps what it played and uploads it.
3. The merge adds the finished lines to the results. A new result outside the interval of a stored one for the same pairing is a warning annotation (`League drift`) and a line of the summary; both stay in the file. Then wave 2 is planned from the merged results: the nearest opponents of the releases that had their first games in wave 1. It plays the same way, in the time that remains less 15 minutes for the publication; when none remains, wave 2 is skipped, the summary says so, and its lines wait for the next night. The job limits on the critical path (plan 15, wave 1 115, merge 10, wave 2 at most 105 and the rest of the budget, publication 15) never add up to more than the budget.
4. The publication merges wave 2, generates the leaderboard (with `main`'s journal), writes the run's summary (the plans, the drift, the first rows of the leaderboard) and, unless `publish` is unchecked, commits `games/<game>/league.jsonl` and `LEADERBOARD.md` to `league-results` as `chore(<game>): league night <date>`. A rejected push (another game's night) is fetched and applied again, up to 5 times; nothing is forced. If a night played a release's first games, it also uploads their sample as `league-game-records-<game>` and starts `archive.yml` for it, which adds it to the game's archive.

By hand: `gh workflow run league-nightly.yml -f game=ice-and-fire` plays one game's night and publishes it. `-f publish=false` is a dry run: it plays and merges and writes the summary, and pushes and starts nothing. A run by hand of a game that has no nightly league works only as a dry run. The branch `league-results` holds only each game's `league.jsonl` and `LEADERBOARD.md` and is never merged; a game with no `league.jsonl` on `main` or on the branch has no night. After a replay of a game's history ([ADR 0048](adr/0048-ice-and-fire-codingame-speed.md), decision 5) merged into `main`, delete or reset `league-results` for that game first, or the next night would take the old results.

**The weekly branch.** `league-weekly.yml` starts on Mondays at 05:30 UTC. For each game whose `league.jsonl` on `league-results` is ahead of `main`'s, it pushes the branch `claude/league-results-<date>`, made from `main`, with that file and a `LEADERBOARD.md` generated from it with `main`'s journal, so that the `League results` check passes. It opens no pull request, since GitHub runs no CI on a pull request that a workflow opens with its token: a weekly Claude task opens it at 06:00 and does nothing else ([ADR 0051](adr/0051-weekly-league-pull-request.md)), and the owner approves it like any other. A game whose `main` results are not the beginning of the branch's is left out with a warning. Nothing ahead, nothing pushed. Run by hand with `gh workflow run league-weekly.yml`.

## Rules for every change

- Claude works on `claude/`-prefixed branches and opens a pull request. It merges only what the owner approved in the conversation, and records the approval on the pull request ([ADR 0006](adr/0006-human-approves-merges.md), [ADR 0023](adr/0023-chat-approved-merges.md)).
- One topic per pull request; one experiment per candidate pull request.
- A decision that is costly to reverse is proposed to the owner first, then recorded as an ADR.
- Tests, the referee and CI checks are never weakened to make a change pass.
- Pull request titles and commit subjects name a game or a framework area as their scope; decision records name a game or `framework` ([ADR 0022](adr/0022-scopes-and-names.md)). A workflow labels pull requests by the paths they change and checks their titles.
- Finished branches are deleted ([ADR 0021](adr/0021-prune-finished-branches.md)): merged ones by GitHub on merge, the others by the weekly Prune branches workflow once their content is safe. When Claude reads a training run, it copies the run's `report.md` to `games/<game>/training/runs/<run>/` in the next pull request, so that the run's branch can go.

## Claude Code setup (Phase 5)

Phase 5 has been in progress since 2026-10-09. Its goal is that the owner only arbitrates and Claude moves work forward between the owner's visits. The plan, with its checklist and gate, is in the [roadmap](ROADMAP.md#phase-5-autonomy-and-workflow). In short:

- **Instructions:** `CLAUDE.md` holds the rules for every session.
- **Agents** in `.claude/agents/`: `implementer` (Sonnet) codes to a precise spec; `pr-reviewer` (Opus) reviews every pull request at a depth matched to its risk; `rules-reviewer` (Opus) checks engine and referee changes against the game's `RULES.md`; `game-reviewer` (Haiku) reviews one recorded game and `review-summarizer` (Haiku) summarizes a batch of reviews or interprets a metrics report of a large batch, through the skill `review-games` ([ADR 0043](adr/0043-game-reviews-by-haiku.md), [ADR 0044](adr/0044-metrics-reports.md)). Claude's main session plans, splits the work, checks the results and merges what the owner approved.
- **Skills** in `.claude/skills/`: the steps that repeat. `land-work` plans and lands work across pull requests, `review-pr` chooses the review's depth, `github-api` has the recipes that work from Claude's sessions, `ask-decision` and `write-adr` bring decisions to the owner and record them; `new-game`, `game-intake`, `game-model`, `rules-check`, `game-research` and `game-retrospective` carry a new game through its stages ([playbook](NEW_GAME.md)); `run-experiment`, `deliver-release`, `training-run`, `review-games` (reviews of recorded games by Haiku agents) and `docs-refresh` cover the rest, and `handoff` keeps `HANDOFF.md` on the branch `claude/handoff`: what waits for the owner, open questions, follow-ups and notes, read at the start of every session ([ADR 0024](adr/0024-handoff-branch.md)). Token use is not measured or reported ([ADR 0034](adr/0034-no-usage-monitoring.md)).
- **Merge policy:** the owner approves every merge in the conversation and Claude carries it out ([ADR 0023](adr/0023-chat-approved-merges.md)). The plan lets Claude merge some classes of change without asking, in a later decision record, and keeps the rest with the owner.
- **Decisions:** asked in the conversation, each with options and a recommendation; when the owner is away, one push notification and `HANDOFF.md` say one is waiting. Only answers in the conversation count.
- **No scheduled session:** the daily report stopped on 2026-10-13 at the owner's request ([ADR 0033](adr/0033-no-daily-scheduled-session.md)); the owner learns what waits for him in the conversation and from `HANDOFF.md`.
