# 0056. Game analysis: CodinGame games recorded, rebuilt and analysed by a generic framework

- Status: accepted (owner, 2026-11-06)
- Date: 2026-11-06
- Scope: framework

## Context

Our bots are judged against each other (the SPRT, the league) and only rarely against the players who rank above us on CodinGame. On 2026-11-06 the owner asked for a tool to record and analyse games, ideally from the top of the ladder, to identify their strategies: playing a release many times against top bots, finding games, or getting games of top bots. He asked for "a generic framework, only applied to the game A Code of Ice and Fire" at first, with a reporting tool "adaptable for various game types".

What CodinGame's public API allows ([ADR 0047](0047-codingame-api.md); its reference, read 2026-11-06):

- It lists only the user's own games: the ranking games ("battles") of a submission, newest first, and the user's test games. Games between two other players cannot be listed; a ranking game whose id is known can still be read, unless its challenge disables replays.
- A game's log has the game options (A Code of Ice and Fire: the map seed), every player's output at every turn, the ranking and the scores; the user's own debug output only in test games.
- Test games can be played against the players of the user's league and the lower ones; in A Code of Ice and Fire the account is in Legend, so all of the top players (925 opponents on 2026-11-06). One at a time; 80 an hour and 600 a day, shared with the owner's own use. A test game can take fixed game options, or replay one of the user's ranking games (same options, same opponents, same seats) with new code.
- The account's current A Code of Ice and Fire submission (`ice-and-fire-v014`) has played over a hundred ranking games against Legend players; the log of one of them, 42 answers long, is 15 KB.

The repository already has the pieces of an offline analysis: one record format for a game ([ADR 0027](0027-game-records.md)), a game's review binary that replays a record into a trace (boards, metrics, phases, decisive moments), the shared crate `cg-review` that turns traces into game files, summaries and metrics reports ([ADR 0043](0043-game-reviews-by-haiku.md), [ADR 0044](0044-metrics-reports.md)), and banks of positions that a bot built for analysis reads.

The owner answered the framing questions in forms on 2026-11-06: A Code of Ice and Fire first; four sources (our past ranking games, new test games, replays of ranking games, local arena games); the goal is the top bots' strategies and our weaknesses; the top 10 as opponents; per-turn metrics, patterns and phases, and a comparison with what our current release would play; Markdown reports; raw logs on a branch that is never merged; about 100 test games a batch, on a fixed set of maps, run on demand from a session; a shared core with a game part; first reports as one profile per top bot.

## Decision

1. **A generic framework, applied first to A Code of Ice and Fire.** The framework fetches, stores, converts and analyses CodinGame games of any two-player game; a game plugs in a small set of parts (decision 7). Nothing in the framework names a game, and the reports are built from generic data that each game labels. The design is [docs/GAME_ANALYSIS.md](../GAME_ANALYSIS.md).
2. **CodinGame's API is called from a script; everything else runs offline.** `scripts/codingame.sh` fetches ranking games and logs, plays test-game batches and replays, with `curl` and `jq`, the token of ADR 0047 and the API's limits (it waits when told to, and resumes a batch where it stopped). The analysis is Rust that reads stored files only, so it runs anywhere, CI included, and no HTTP client joins the workspace's dependencies.
3. **Raw logs live on the branch `claude/codingame-games`, which has no pull request and is never merged; reports live in `main`.** Sessions push it as they push `claude/handoff` ([ADR 0024](0024-handoff-branch.md)), since they may push only to `claude/` branches ([ADR 0021](0021-prune-finished-branches.md)), and the pruning keeps a branch without a pull request. The branch holds each game's log as the API gave it and an index of the games (where each comes from, the players, the result) and snapshots of the leaderboard taken at each fetch, which give the players' ranks: game logs and the list of ranking games give none. Reports are Markdown under `games/<game>/research/codingame/`, with their numbers, and name the batch they read.
4. **A CodinGame game is rebuilt and checked before it is analysed.** It is converted into the record format of ADR 0027, which gains an optional origin (CodinGame's game id, the kind of game, each player's agent id and rank) and a new format version. The game's engine replays it: every command must be accepted, and the result must be CodinGame's. A game that disagrees is left out of the analysis and listed in the report, as a possible rule difference to look into.
5. **Four sources, one format.** Our submission's ranking games (all of them, the top 10 reported apart); test-game batches of a frozen release against chosen opponents; replays of our ranking games with another release; and the arena's records of local games, which are already in the format. Games of other players whose ids the owner gives (from CodinGame's website) can be fetched the same way; ids are never guessed or scanned.
6. **Test-game batches run on demand from a session, within ADR 0047.** About 100 games a batch, 10 against each of the top 10 of the leaderboard at the time, on a fixed set of maps kept in `games/<game>/codingame-seeds.txt`. The code sent is a release file unchanged; the owner's IDE code and settings are never touched. The script plans the batch without playing unless asked to play. The SPRT and the league remain the judges of strength.
7. **What a game provides.** To join, a game provides: the conversion of a log's frames into its turns' answers and of the game options into a seed; the replay of a record into a trace with its metrics and decisive moments (A Code of Ice and Fire's review binary already does it; a game without one adds one); the events it counts at each ply; the opening of a side as short tokens, comparable across seats; and, for the comparison with our moves, a position and the move played as a judge reads them, the judge's answer read back (its own move and its scores of both), and how two moves compare. A Code of Ice and Fire's judge is a new `judge` mode of the plan bot's analysis build, which scores a given plan besides choosing its own.
8. **The analysis is generic.** On top of the traces, the framework builds a profile of each player (results against us by seat, metric curves by turn and phase, when each kind of event and decisive moment first happens, how its wins come, its usual openings), lists our weaknesses (the decisive moments of our losses, by phase and by opponent), and compares, ply by ply, what a top player played with what the judge (the current release) would play and how the judge scores both.
9. **Built in steps, one pull request each:** this design; the script, the stored format and the record's origin; A Code of Ice and Fire's conversion and its check against CodinGame's results; the profiles and the report on our past ranking games; the test-game batches and replays; the plan bot's `judge` mode and the comparison with it.

## Consequences

- The top players' play can be studied from real games with the same tools as our own games, and any game the framework adds gets the same reports once it provides decision 7's parts.
- Our games against them on CodinGame also check our engine against CodinGame on every game converted (decision 4), as the rules-check bot did once.
- Test-game batches use the owner's shared quota: the limits let a batch of about 100 games start within about 70 minutes (80 an hour), longer if CodinGame's games are slow, since they run one at a time; a batch leaves him most of the day's 600.
- Games between top players cannot be found through the API: what is learned about them comes from their games against us, and from games whose ids the owner gives (decision 5).
- The record format changes version (ADR 0027): the studio and the review binaries keep reading older records.
- Other players' outputs are stored on a public branch of a public repository. CodinGame shows the same games to every visitor as replays; whether its terms allow republishing logs was not checked; the owner chose to store the logs in full (2026-11-06).
- Players with more than two seats, and games with no opponent, are outside the framework: the record and the trace are two-seat, as the framework's games are; the new index and profiles keep players as lists, so a later change to the record would be the main step for them.
